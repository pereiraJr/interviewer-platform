# Phase 1 Data Model: Deployment Seed Data

**Feature**: `002-deployment-seed-data` | **Date**: 2026-10-07

## Overview

This feature introduces **no new persisted entity and no new collection**. It writes the
existing **Job** entity (defined in `001-jobs-dashboard`) into MongoDB's `jobs` collection from
a version-controlled **Seed Dataset**. The only new domain concept is the dataset itself, which
is code, not a stored collection.

## Entity: Job (reused — owned by `001-jobs-dashboard`)

Stored in the `jobs` collection. Field definitions and public projection are unchanged; see
`specs/001-jobs-dashboard/data-model.md`. Summary of what seeding must satisfy:

| Field | Type | Required | Constraints / Rules for seeded rows |
|-------|------|----------|-------------------------------------|
| `_id` | ObjectId | yes | Generated by the server on insert (not supplied by the dataset). |
| `title` | string | yes | Non-empty after trim; ≤ 200 chars. |
| `description` | string | no | Trimmed; ≤ 500 chars; may be absent. |
| `status` | `"available" \| "closed"` | yes | Must be one of the two values; seeded dataset includes both. |
| `createdAt` | Date | yes | Set to the seed run time. |
| `updatedAt` | Date | yes | Set to the seed run time. |

**Public projection consumed by the dashboard** (unchanged, `JobSummary`): only `id`, `title`,
`description`; `status` is internal and used solely to filter `available` jobs.

## Entity: Seed Dataset (new — code module, not persisted)

| Attribute | Type | Rules |
|-----------|------|-------|
| `sampleJobs` | `NewJob[]` | Version-controlled baseline; each row validated before use. |
| `NewJob` | type | `Omit<JobDocument, '_id' | 'createdAt' | 'updatedAt'>` — i.e. `{ title, description?, status }`. |

- **Composition**: a small fixed sample catalogue. MUST contain at least one `available` job
  (so the dashboard is non-empty) and at least one `closed` job (to prove availability filtering
  still applies to seeded data).
- **Versioning**: committed to the repository alongside the application; every deployment ships
  the same reviewable baseline (FR-007).
- **Ownership**: the `jobs` collection is seed-owned in this slice; the dataset is authoritative
  and is re-applied wholesale on each run.

## Operation: `seedSampleJobs(db): Promise<number>`

1. Validate every row in `sampleJobs` against the model rules. If any row is invalid, **abort
   before writing** and throw.
2. `deleteMany({})` on the `jobs` collection.
3. `insertMany(sampleJobs` with `createdAt`/`updatedAt` set to the run time`)`.
4. Return the number of documents inserted.

### Idempotency & state semantics

| Scenario | Expected state |
|----------|----------------|
| Empty database, run once | `jobs` contains exactly the baseline documents. |
| Run N times | `jobs` contains exactly the baseline documents; no duplicates. |
| Interrupted mid-insert | Collection is partial; a subsequent run deletes and rewrites the baseline (converges). |
| Empty dataset | `deleteMany` runs; 0 inserted; reported as `0`, not an error. |
| Invalid row present | No `deleteMany`/`insertMany` executed; operation throws; existing data preserved. |

### Isolation guarantee

Seeding operates on the single `jobs` collection only. It MUST NOT read or write any other
collection (notably future `sessions`/`transcripts`/`evaluations`), satisfying FR-006.

## Validation Rules (mapped to requirements)

| Rule | Source |
|------|--------|
| Every seeded row has a valid non-empty `title` (≤ 200) | FR-009; `001` FR-003 |
| `description` bounded to 500 chars, absent allowed | `001` FR-004/FR-012 |
| `status` ∈ {`available`, `closed`} | `001` FR-001 (availability filtering) |
| Validation happens before any write; invalid data fails loudly | FR-009; constitution |
| Repeated runs produce no duplicates | FR-004, SC-002 |
| Only the `jobs` collection is written | FR-006, FR-008 |

## Relationships

- **Seed Dataset → Job**: one-to-many (the dataset produces the job documents on each run).
- No relationships to `001`'s future session/transcript/evaluation entities exist; those are
  explicitly out of scope and MUST remain untouched.

## Volume Assumptions

- Tiny batch: the baseline is on the order of a handful of jobs (≈6), so `deleteMany` +
  `insertMany` completes in a few seconds at most (SC-005).
